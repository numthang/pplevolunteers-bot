# Kanban — ช่องข้อมูลตั้งเอง (custom fields)

> **สถานะ:** 🟡 ออกแบบไว้ล่วงหน้า **ยังไม่ทำ และยังไม่ควรทำ** (เคาะ 2026-08-15)
> เอกสารนี้มีไว้เพื่อ **กันไม่ให้วันนี้เดินไปในทางที่พรุ่งนี้เพิ่มไม่ได้** ไม่ใช่สเปกที่รอ implement
>
> ที่มา: import ข้อมูลเก่าจาก AppFlowy (`backups/kanban/kanban_import.xlsx` · 83 การ์ด) แล้วเจอ 6 field ที่ระบบยังไม่มี

---

## 🎯 คำตัดสิน: ยังไม่ทำ — และนี่คือเหตุผลที่ไม่ใช่ "ขี้เกียจ"

ข้อมูลจริง 83 การ์ดมี 6 field ที่เราไม่มี แต่พอแยกตามชนิดแล้วเหลือแค่ **3 แบบ**:

| field ที่ทีมใช้จริง | จริงๆ แล้วคือ | มีในดีไซน์อยู่แล้วไหม |
|---|---|---|
| category · อำเภอ · อุปกรณ์ | เลือกหลายค่าจากรายการ | ✅ **ป้าย** (`kanban_labels` ก้อน 6) |
| Discord + FB เก่า | ลิงก์ไปของข้างนอก | ✅ **ลิงก์** (`kanban_card_links` ก้อน 4) |
| งบประมาณ | ตัวเลข | ❌ ไม่มี |

**5 จาก 6 แก้ได้ด้วยของที่วางไว้แล้ว** → สร้าง "ระบบ custom field" ทั้งระบบเพื่อรองรับข้อมูล **ทีมเดียว** คือ over-engineering ตรงตามที่ `KANBAN.md` เตือนเรื่องเดินทาง Notion

### ⛔ "FB Post" ไม่ต้องเป็น field — ตัดทิ้งแล้ว (เคาะ 2026-08-15)

ระบบเก็บลิงก์โพสต์ที่เผยแพร่แล้วอยู่ก่อนแล้วที่ `post_social_history.result` → `{"url": "https://www.facebook.com/permalink.php?..."}`

พอผูกการ์ด ↔ โพสต์ (ก้อน 4-5) ลิงก์จะโผล่เอง **ไม่ต้องมีใครพิมพ์** — ตรงกับแก่นของดีไซน์: ห้ามให้คนกรอกข้อมูลเดียวกัน 2 รอบ

> ⚠️ **ข้อยกเว้นตอน import:** 33 ลิงก์เก่าในไฟล์ไม่ได้โพสต์ผ่านระบบเรา (ลงมือบน FB โดยตรง) ระบบไม่มีทางรู้จัก
> → ลงตาราง **ลิงก์ภายนอก** ตัวเดียวกับลิงก์ Discord · ห้ามสร้าง field `fb_post` แยก

## 🚦 เส้นที่ต้องกลับมาทำ (tripwire)

ทำเมื่อ **ข้อใดข้อหนึ่ง** เกิดขึ้น — ไม่ใช่ก่อนหน้านั้น:

1. **ทีมที่ 2 ขอ field ที่ทีมแรกไม่ใช้** ← สัญญาณที่แท้จริง เพราะตอนนั้นถึงจะรู้ว่าอะไรคือ *รูปแบบร่วม* ไม่ใช่เดาจากตัวอย่างเดียว
2. มีคนขอ field ใหม่ **เกิน 3 ครั้งใน 1 เดือน** จนการเพิ่มคอลัมน์ทีละอันช้ากว่าทำของกลาง
3. เริ่มมี org ที่ 2 ที่ไม่ใช่ราชบุรีใช้โมดูลนี้จริง

**ถ้ายังไม่ถึงเส้น:** field ใหม่ = เพิ่มคอลัมน์ตรงๆ ถูกกว่าและเร็วกว่าเสมอ

## ⛔ อะไรที่ห้ามยัดเข้า custom field เด็ดขาด (สำคัญที่สุดในเอกสารนี้)

**กติกา: ถ้าระบบต้อง "คิด" กับค่านั้น มันต้องเป็นคอลัมน์จริง ไม่ใช่ custom field**

| ข้อมูล | เป็นอะไร | เพราะ |
|---|---|---|
| `status_type` | 🔒 คอลัมน์จริง | **ห้ามที่สุด** — สถานะอยู่ 2 ที่เมื่อไหร่ = บอร์ดโกหก = ทั้งดีไซน์พัง (`KANBAN.md` §กฎเหล็ก) |
| `owner_user_id` · คนช่วย | 🔒 คอลัมน์จริง | "การบ้านของฉัน" กรองด้วยสิ่งนี้ |
| `due_at` · `start_at` | 🔒 คอลัมน์จริง | ต้องเรียง · เตือนเลยกำหนด · DM สรุปเช้าอ่านค่านี้ |
| `blocked` | 🔒 คอลัมน์จริง | เป็นธงที่ UI ทุกที่ต้องเห็น |
| ป้าย | 🔒 ตารางของตัวเอง | เป็น concept มาตรฐานของ kanban ทุกเจ้า มี UI เฉพาะ (ชิปสี + ตัวกรอง) · Jira/Linear ก็มีป้าย **คู่กับ** custom field ไม่ได้ยุบรวมกัน |
| ลิงก์ไป เคส/โพสต์/URL | 🔒 ตารางของตัวเอง | ก้อน 4 **คำนวณสถานะสด** จากลิงก์ ไม่ใช่ข้อมูลตายๆ |
| **งบประมาณ · อุปกรณ์เสริม · อะไรที่ระบบแค่แสดง** | ✅ custom field ได้ | ระบบไม่ต้องเข้าใจความหมาย |

> **วิธีตัดสินเร็ว:** ถ้าลบ field นั้นทิ้งแล้วมีโค้ดพัง → คอลัมน์จริง · ถ้าแค่ช่องว่างบนจอ → custom field

## 🗄️ โครงที่วางไว้ (ยังไม่สร้าง)

```
kanban_field_defs
  id · org_id            ← scope ที่ org เสมอ
  board_id               ← NULL = ใช้ได้ทุกกระดาน · มีค่า = เฉพาะกระดานนั้น (ก้อน 3 ขึ้นไป)
  key                    ← ชื่อในโค้ด ไม่เปลี่ยนตามชื่อที่โชว์
  label · help_text
  type                   ← 'text' | 'number' | 'date' | 'select' | 'multi_select' | 'url' | 'checkbox'
  options jsonb          ← ใช้เฉพาะ select/multi_select
  required bool
  sort_order · archived_at
  UNIQUE (org_id, board_id, key)

kanban_card_field_values
  card_id · field_id
  value_text · value_num · value_date · value_bool · value_options (int[])
                         ← คอลัมน์แยกตามชนิด **ไม่ใช่ jsonb ก้อนเดียว**
  PRIMARY KEY (card_id, field_id)
```

**ทำไมแยกคอลัมน์ตามชนิด ไม่ใช้ jsonb ก้อนเดียว:** วันที่ต้องกรอง "งบเกิน 20,000" หรือเรียงตามตัวเลข jsonb จะต้องแคสต์ทุกแถว + index ยาก · แยกคอลัมน์ทำให้ index ปกติใช้ได้เลย และ DB บังคับชนิดให้ (ตัวเลขที่กรอกเป็นตัวหนังสือจะ error ตั้งแต่ insert ไม่ใช่ไปพังตอน SUM)

**`archived_at` ไม่ใช่ DELETE:** ลบ field ที่มีคนกรอกไปแล้ว = ข้อมูลหายเงียบ · ซ่อนแทน แล้วค่อยมีปุ่มลบถาวรที่บอกจำนวนแถวที่จะหาย

## ✅ สิ่งที่ต้องทำ (และไม่ทำ) วันนี้ เพื่อไม่ให้ทางตัน

| ตอนนี้ | ทำไม |
|---|---|
| ✅ `start_at` เป็น **คอลัมน์จริง** | ระบบต้องเรียง/เตือน — ถ้าเผลอทำเป็น custom field จะย้ายยากมาก |
| ✅ ป้าย + ลิงก์ เป็น **ตารางจริง** ตามดีไซน์เดิม | ห้ามรอ custom field มาแทน จะได้ 2 กลไกทำเรื่องเดียวกัน |
| ⚠️ **งบประมาณ** — ถ้าใส่เป็นคอลัมน์วันนี้ ต้องรู้ตัวว่าวันหน้าจะย้ายมาเป็น custom field | เป็นตัวที่ "custom field ที่สุด" ในกอง · ยอมรับหนี้ตรงนี้ได้ แค่อย่าลืมว่ามี |
| ⛔ **ห้ามสร้างคอลัมน์ `extra jsonb` แบบกันเหนียว** | จะกลายเป็นถังขยะที่ไม่มี schema ไม่มี validation แล้วสุดท้ายต้องมาแกะทีหลัง — แย่กว่าไม่มีอะไรเลย |
| ⛔ **ห้ามให้ custom field มีชนิด "status"** ตอนสร้างจริง | ปิดประตูนี้ไว้ตั้งแต่วันแรก |

## 📎 บันทึกจากข้อมูลจริง (ใช้ตอนออกแบบรอบหน้า)

- **multi-select คือชนิดที่ใช้หนักสุด** — 3 จาก 6 field เป็น multi-select (category 13 ค่า · อำเภอ 11 · อุปกรณ์ 22)
  → Trello ทำ multi-select ไม่ได้ (เลือกได้ค่าเดียว) ถ้าลอก Trello ตรงๆ จะไม่พอใช้ตั้งแต่วันแรก
- **`อำเภอ` อาจไม่ใช่ custom field แต่เป็น scope** — ระบบมี geography/scope อยู่แล้ว ถ้าทำเป็นพื้นที่จริง ผู้ประสานงานอำเภอจะกรอง "งานในพื้นที่ฉัน" ได้
  ⬜ **ยังไม่เคาะ** — ต้องตัดสินก่อน import ว่าจะลงเป็นป้าย หรือลงเป็น scope
- **`อุปกรณ์` อาจเป็น checklist มากกว่า field** — เป็นรายการของที่ต้องขนไปงาน ไม่ใช่คุณสมบัติของงาน
