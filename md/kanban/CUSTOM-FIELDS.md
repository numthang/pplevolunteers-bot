## 🔄 กลับคำรอบเย็น (2026-08-18) — select/multi_select เร่งมาทำพร้อมก้อน 2 + checklist กลายเป็น custom field

user ส่งสกรีนช็อตจริงของ AppFlowy มา 2 ภาพระหว่างเขียนก้อน 2 (5 ชนิดสเกลาร์) แล้วขอเปลี่ยนแผนกลางคัน:

| แผนเดิม (ขั้น 2-3 แยกกัน) | ตอนนี้ | ทำไม |
|---|---|---|
| ขั้น 2 = 5 ชนิดสเกลาร์เท่านั้น · select/multi_select รอขั้น 3 | **ทำพร้อมกันเลย** | user เห็นภาพ UI จริงแล้วอยากได้เลย ไม่ต้องรอ |
| "งานย่อย" (checklist) เป็นคอลัมน์จริงเสมอ (เส้นแบ่งเดิมต้นแผน) | **checklist เป็น custom field type** | user: *"ตอนแรกผมจะทำเป็น field มาตรฐาน ใช่ไหม แต่เปลี่ยนใจละ ทำเป็น custom field ไปเลย"* — AppFlowy เองก็มี Checklist เป็น field_type ตัวที่ 7 อยู่แล้ว (§ดีไซน์ AppFlowy ข้างล่าง) ไม่ใช่เรื่องแปลก |
| ขั้น 3 วางแผนหน้า `/kanban/fields` (แอดมิน) + `LabelManager.jsx` ก็อปโครง | **ไม่มีหน้าแอดมินเลย** | user เห็นสกรีนช็อต option picker ของ AppFlowy ที่ rename/สี/ลบ/ลากจัดลำดับทำ**ในตัว combobox เอง** แล้วถาม *"ด้วยวิธีนี้ไม่ต้องมี field manager ให้ยุ่งยาก ถูกไหม"* → ใช่ ตัดออกทั้งหน้า |

**ผลของการตัด field manager ออก:**
- ไม่มี `isKanbanAdmin` gate ในระบบ custom field เลย (fields + options + checklist) — ใครก็ตามที่ `canEditCard` การ์ดใบนั้นได้ จัดการ field/option/checklist ได้หมด
- `key` ของ field **สร้างอัตโนมัติจาก label** (`slugifyFieldKey` — ไทยล้วน slug ไม่ได้ fallback เป็น `field_<id>`) — คนไม่ต้องพิมพ์เอง เพราะไม่มีฟอร์มแอดมินให้กรอกแล้ว
- ตัวเลือกของ select/multi_select (`kanban_field_options`) จัดการทั้งหมดใน `TagCombobox.jsx` — สร้าง/เปลี่ยนชื่อ/สี/ลากจัดลำดับ/"ลบ" (= archive จริง กันข้อมูลหายเงียบเหมือนป้าย)
- **ไม่มีข้อมูลจริงใน `kanban_card_checklist` เลยตอนกลับคำ** (โมดูลยังไม่เคย deploy) → เปลี่ยนกลไกได้เต็มๆ ไม่ต้อง migrate ข้อมูล แค่เพิ่มคอลัมน์ `field_id` แล้วผูกใหม่

## 🔄 กลับคำ 2 ข้อ (2026-08-18) — และเหตุผล

| ฉบับ 15 ส.ค. | ตอนนี้ | ทำไม |
|---|---|---|

| "category/อำเภอ/อุปกรณ์ → ใช้ป้ายแทน" | **ยุบป้ายเข้า custom field** | คำตอบเดิมเอา 2 คำถามมาปนกัน (ดูข้างล่าง) |

**ที่ผมพลาดคือเอา 2 คำถามคนละเรื่องมาตอบรวมกัน:**

1. *"status/เจ้าภาพ/กำหนดส่ง ควรเป็น custom ไหม"* → **ไม่ควร — ข้อนี้ยังถูกและไม่มีวันเปลี่ยน**
2. *"category/อำเภอ/อุปกรณ์ ควรเป็น custom ไหม"* → ตอบว่า "ใช้ป้าย" **เพราะตอนนั้นไม่อยากสร้าง custom field**
   ไม่ใช่เพราะป้ายเป็นบ้านที่ถูก → **พอสร้าง custom field แล้ว เหตุผลนั้นหายทั้งอัน**

**และของ 2 อย่างนี้คือสิ่งเดียวกันเชิงโครงสร้าง** (user ทักเอง 2026-08-18):

```
ป้าย:          กลุ่ม "อำเภอ"  →  โพธาราม · บ้านคา · ทีมจังหวัด
custom field:  field "อำเภอ"  →  โพธาราม · บ้านคา · ทีมจังหวัด   (type=multi_select)
```

กลุ่มป้าย = field · ป้ายในกลุ่ม = options — ต่างกันแค่ป้ายเป็นของ org ทั้งใบ ส่วน field มี `board_id` เลือกได้
→ **ยุบเป็นกลไกเดียว** (ขั้น 3 ของแผน) · UI ที่ทำไปแล้ว (ชิปสี/กล่องเลือก/ตัวกรอง/หน้าจัดการ) ใช้ต่อได้ เปลี่ยนแค่แหล่งข้อมูล

## 🔬 ดีไซน์ AppFlowy ของจริง (ไปดูมา 2026-08-18)

- **Postgres ของ AppFlowy-Cloud ไม่มี schema ของ field** — field/cell อยู่ใน collab document (CRDT blob · ก้อนใหญ่ไป MinIO)
  → `pg_dump` จาก docker ที่ user รันอยู่ **ไม่ช่วยอะไร** ไม่ต้องเสียเวลาไปแกะ
- ของจริงอยู่ในซอร์ส (flowy-database):
  `Field { id, name, field_type(0=Text 1=Number 2=Date 3=SingleSelect 4=MultiSelect 5=Checkbox 6=URL 7=Checklist), type_options: Map<FieldType,TypeOption> }`
  · cell = `(row_id, field_id) → ค่าก้อนเดียว` ตีความตามชนิด

**ลอก 2 อย่าง:**
1. ชุดชนิด + แนวคิด `type_options` เป็น **Map เก็บ config ของทุกชนิดที่ field นั้นเคยเป็น** → สลับชนิดไปกลับไม่เสียค่าเดิม
2. **ตัวเลือกของ select อยู่ "ในตัว field" ไม่ใช่คลังกลาง** (`SelectTypeOption.options[] = {id,name,color}`) → ยืนยันทางยุบป้ายเข้า field

**ไม่ลอก storage:** cell เป็น blob ก้อนเดียวใช้ได้เพราะ AppFlowy คำนวณทุกอย่างในเครื่องบน CRDT
เราเป็นเว็บบน Postgres ที่ต้อง `WHERE งบ > 20000` / `SUM()` / เรียงตามตัวเลข → **คอลัมน์แยกตามชนิด** (ดู §โครง)

## 🧭 ทำไมเป็น hybrid (บาง field ตายตัว บาง field ตั้งเอง) — ไม่ใช่การประนีประนอม

> คำถามที่ user ถาม 2026-08-15: *"เดี๋ยวมี fix เดี๋ยวมี custom มันโอเคป่ะ หรือควร custom ทั้งหมดเหมือน AppFlowy/Notion/Trello"*

**ของจริงที่แต่ละเจ้าทำ:**

| | ตายตัว | ตั้งเอง |
|---|---|---|
| **Trello** | list · สมาชิก · ป้าย · กำหนดส่ง · checklist | Custom Fields เป็นของเสริม |
| **Jira** | status · assignee · priority · resolution | custom field — **บานปลายจนเป็นตำนาน** องค์กรใหญ่มีเป็นพันตัวจนระบบช้า |
| **Linear** | เกือบทั้งหมด ตั้งใจให้ตัวเลือกน้อย | แทบไม่มี |
| **Notion / AppFlowy** | แทบไม่มีอะไร | ทุกอย่าง |

**หมัดชี้ขาด:** Notion เองสุดท้ายต้องเพิ่ม property ชนิดพิเศษชื่อ **Status** ที่มีการจัดกลุ่ม To-do / In progress / Complete ติดมาให้
เพราะ property ธรรมดา**ทำ board ไม่ได้** — ระบบต้องรู้ว่าค่าไหนแปลว่า "จบแล้ว" ถึงจะขีดฆ่า/นับ/เตือนได้
เจ้าที่ full-custom ที่สุดในโลกยังต้องยอมมีของตายตัว

### ทำไม *เรา* ยิ่ง full-custom ไม่ได้

ระบบเราทำ 4 อย่างที่ต้อง **เข้าใจความหมาย** ไม่ใช่แค่เก็บค่า:

```
"การบ้านของฉัน" รวมงานข้ามทีม   → ต้องรู้ว่าใครคือเจ้าภาพ
เตือนเลยกำหนด + DM สรุปทุกเช้า    → ต้องรู้ว่าอันไหนคือกำหนดส่ง
ช่องบนกระดาน                      → ต้องรู้ว่าอันไหนคือสถานะ
เคสปิด → การ์ดขึ้น "เสร็จ" เอง    → ต้องรู้ทั้งสองฝั่ง
```

ถ้าสถานะเป็น custom field แล้ววันหนึ่งมีคนลบทิ้ง / ตั้งชื่อใหม่ / กระดานที่สองตั้งคนละแบบ
→ **บอทไม่รู้ว่าจะอ่านอะไรตอนส่ง DM ตอนเช้า** · นี่คือเหตุผลที่ Notion ไม่มีหน้า "งานของฉัน" ที่รวมข้ามฐานข้อมูลได้จริง

**และมันทิ้งข้อเดียวที่เราเก่งกว่าเขา** — `KANBAN.md` เขียนไว้ว่าจุดแข็งคือ *งาน ↔ เคสจริง ↔ โพสต์จริง ↔ คนจริง อยู่ฐานเดียวกัน สถานะคำนวณสด*
full-custom = ได้ **AppFlowy ที่ฟีเจอร์น้อยกว่า** = ตรงกับกับดัก *"ถ้าทำแล้วได้ Trello ที่ช้ากว่า Trello แปลว่าดีไซน์ผิด"*

### ปัญหาที่ hybrid มีจริง และวิธีแก้

ปัญหาไม่ใช่การมี 2 แบบ แต่คือ **คนใช้เดาไม่ออกว่าอะไรอยู่แบบไหน** → แก้ที่ทำให้เส้นแบ่งอธิบายได้ในประโยคเดียว:

> **ช่องที่ระบบต้องใช้ทำงานให้คุณ** (ใครทำ · ส่งเมื่อไหร่ · ถึงไหนแล้ว) = **มีให้ตายตัว**
> **ช่องที่เป็นข้อมูลของทีมคุณเอง** = **ตั้งเอง**

**บน UI ต้องแยกกายภาพด้วย** — ของระบบอยู่ข้างบน · ของทีมอยู่ในกล่อง "ข้อมูลของทีม" ข้างล่าง
พอแยกให้เห็นแล้วมันไม่รู้สึกมั่ว (Jira พังตรงนี้เพราะเอา custom field แทรกปนกับของระบบ)

## ⛔ อะไรที่ห้ามยัดเข้า custom field เด็ดขาด (สำคัญที่สุดในเอกสารนี้)

**กติกา: ถ้าระบบต้อง "คิด" กับค่านั้น มันต้องเป็นคอลัมน์จริง ไม่ใช่ custom field**

| ข้อมูล | เป็นอะไร | เพราะ |
|---|---|---|
| `status_type` | 🔒 คอลัมน์จริง | **ห้ามที่สุด** — สถานะอยู่ 2 ที่เมื่อไหร่ = บอร์ดโกหก = ทั้งดีไซน์พัง (`KANBAN.md` §กฎเหล็ก) |
| `owner_user_id` · คนช่วย | 🔒 คอลัมน์จริง | "การบ้านของฉัน" กรองด้วยสิ่งนี้ |
| `due_at` · `start_at` | 🔒 คอลัมน์จริง | ต้องเรียง · เตือนเลยกำหนด · DM สรุปเช้าอ่านค่านี้ |
| `blocked` | 🔒 คอลัมน์จริง | เป็นธงที่ UI ทุกที่ต้องเห็น |
| ป้าย | ✅ **custom field ชนิด `multi_select`** (แก้ 2026-08-18) | เดิมเขียนว่าเป็นตารางของตัวเอง อ้าง Jira/Linear — **ยกเลิก** · กลุ่มป้าย = field · ป้าย = options · UI ชิปสี+ตัวกรองยังอยู่ แค่ขับด้วย field |
| ลิงก์ไป เคส/โพสต์/URL | 🔒 ตารางของตัวเอง | ก้อน 4 **คำนวณสถานะสด** จากลิงก์ ไม่ใช่ข้อมูลตายๆ |
| **งบประมาณ · อุปกรณ์เสริม · อะไรที่ระบบแค่แสดง** | ✅ custom field ได้ | ระบบไม่ต้องเข้าใจความหมาย |

> **วิธีตัดสินเร็ว:** ถ้าลบ field นั้นทิ้งแล้วมีโค้ดพัง → คอลัมน์จริง · ถ้าแค่ช่องว่างบนจอ → custom field

## 🗄️ โครงที่จะสร้าง

> ⚠️ โครงข้างล่างเป็นฉบับ 15 ส.ค. · **ฉบับที่จะลงมือจริงอยู่ในแผน** `~/.claude/plans/reactive-churning-falcon.md`
> ต่างกัน 3 จุด: เพิ่ม `board_id` (NULL = ทุกกระดาน) · เพิ่ม `type_options jsonb` (ลอก AppFlowy) · options แยกเป็นตาราง `kanban_field_options` แทน jsonb (ต้องมี id คงที่ + สี + ซ่อนได้ เหมือน `kanban_labels` เป๊ะ)

```
kanban_field_defs
  id · org_id            ← scope ที่ org เสมอ
  board_id               ← NULL = ใช้ได้ทุกกระดาน · มีค่า = เฉพาะกระดานนั้น (ก้อน 3 ขึ้นไป)
  key                    ← ชื่อในโค้ด ไม่เปลี่ยนตามชื่อที่โชว์
  label · help_text
  type                   ← 'text' | 'number' | 'date' | 'select' | 'multi_select' | 'url' | 'checkbox'
  options jsonb          ← ใช้เฉพาะ select/multi_select
  required bool
  sort_order · archived_at
  UNIQUE (org_id, board_id, key)

kanban_card_field_values
  card_id · field_id
  value_text · value_num · value_date · value_bool · value_options (int[])
                         ← คอลัมน์แยกตามชนิด **ไม่ใช่ jsonb ก้อนเดียว**
  PRIMARY KEY (card_id, field_id)
```

**ทำไมแยกคอลัมน์ตามชนิด ไม่ใช้ jsonb ก้อนเดียว:** วันที่ต้องกรอง "งบเกิน 20,000" หรือเรียงตามตัวเลข jsonb จะต้องแคสต์ทุกแถว + index ยาก · แยกคอลัมน์ทำให้ index ปกติใช้ได้เลย และ DB บังคับชนิดให้ (ตัวเลขที่กรอกเป็นตัวหนังสือจะ error ตั้งแต่ insert ไม่ใช่ไปพังตอน SUM)

**`archived_at` ไม่ใช่ DELETE:** ลบ field ที่มีคนกรอกไปแล้ว = ข้อมูลหายเงียบ · ซ่อนแทน แล้วค่อยมีปุ่มลบถาวรที่บอกจำนวนแถวที่จะหาย

## ✅ สิ่งที่ต้องทำ (และไม่ทำ) วันนี้ เพื่อไม่ให้ทางตัน

| ตอนนี้ | ทำไม |
|---|---|
| ✅ `start_at` เป็น **คอลัมน์จริง** | ระบบต้องเรียง/เตือน — ถ้าเผลอทำเป็น custom field จะย้ายยากมาก |
| ✅ ป้าย + ลิงก์ เป็น **ตารางจริง** ตามดีไซน์เดิม | ห้ามรอ custom field มาแทน จะได้ 2 กลไกทำเรื่องเดียวกัน |
| ✅ **งบประมาณ** เป็น custom field ชนิด `number` (ไม่ต้องเป็นคอลัมน์แล้ว) | ตัวที่ "custom field ที่สุด" ในกอง · พอทำ custom field จริงก็ลงที่นี่ตรงๆ ไม่มีหนี้ |
| ⛔ **ห้ามสร้างคอลัมน์ `extra jsonb` แบบกันเหนียว** | จะกลายเป็นถังขยะที่ไม่มี schema ไม่มี validation แล้วสุดท้ายต้องมาแกะทีหลัง — แย่กว่าไม่มีอะไรเลย |
| ⛔ **ห้ามให้ custom field มีชนิด "status"** ตอนสร้างจริง | ปิดประตูนี้ไว้ตั้งแต่วันแรก |

## 📎 บันทึกจากข้อมูลจริง (ใช้ตอนออกแบบรอบหน้า)

- **multi-select คือชนิดที่ใช้หนักสุด** — 3 จาก 6 field เป็น multi-select (category 13 ค่า · อำเภอ 11 · อุปกรณ์ 22)
  → Trello ทำ multi-select ไม่ได้ (เลือกได้ค่าเดียว) ถ้าลอก Trello ตรงๆ จะไม่พอใช้ตั้งแต่วันแรก
- ~~**`อำเภอ` อาจไม่ใช่ custom field แต่เป็น scope**~~ — **ตกไปแล้ว (2026-08-15)**
  ในลิสต์ 11 ค่ามี **"ทีมจังหวัด"** ปนอยู่ ซึ่งไม่ใช่อำเภอ → เขาใช้ช่องนี้เป็น *ป้ายบอกว่างานของใคร/ที่ไหน* ไม่ใช่ข้อมูลภูมิศาสตร์
  ถ้าทำเป็น geography scope จริงจะพังตั้งแต่แถวแรกที่เจอค่านี้
- **`อุปกรณ์` อาจเป็น checklist มากกว่า field** — เป็นรายการของที่ต้องขนไปงาน ไม่ใช่คุณสมบัติของงาน

### ⚠️ ~~ทางออกที่เคาะแล้ว — "ป้ายที่มีกลุ่ม" ไม่ใช่ custom field~~ (2026-08-15 · **ยกเลิก 2026-08-18**)

> **อ่าน §กลับคำ ข้างบนก่อน** — ข้อสรุปของหัวข้อนี้ถูกแทนที่ด้วย "ยุบป้ายเข้า custom field"
> ส่วนที่ยังจริงอยู่คือ *เหตุผลว่าทำไมห้าม hardcode `district`* และ *ทำไมต้องมีกลไกเดียว ไม่ใช่ 2*

user ทักว่า `อำเภอ` กับ `งบประมาณ` **ไม่ควร fix** — เห็นด้วย โดยเฉพาะ `อำเภอ` เพราะ geography ที่ hardcode แบบ PPLE
เป็นตัวขวางไม่ให้ระบบไปใช้กับ org อื่นอยู่แล้ว (org กรุงเทพใช้เขต · ทีมชาติใช้ภาค) — ยัด `district` ลง `kanban_cards` = ทำผิดซ้ำที่เดิม

**แต่ทางออกไม่ใช่ให้ทั้งคู่เป็น custom field** เพราะจะได้ 2 กลไกทำเรื่องเดียวกัน (category = ป้าย แต่ อำเภอ = custom field ทั้งที่หน้าตาการใช้งานเหมือนกันเป๊ะ)

```
ป้าย: name · color · group
  กลุ่ม "สายงาน"  → สมาชิกสัมพันธ์ · ทีมสื่อ · ลงพื้นที่ …
  กลุ่ม "พื้นที่"  → ทีมจังหวัด · โพธาราม · บ้านคา …
  กลุ่ม "อุปกรณ์" → เต็นท์ · โต๊ะ · ปริ้นเตอร์ …
```

**ไม่มีคำว่า "อำเภอ" อยู่ในโค้ดเราสักที่** — ทุกอย่างเป็นข้อมูลที่ org ตั้งเอง ตอบโจทย์ "ไม่ fix" โดยไม่ต้องมี 2 กลไก
→ **เหลือ `งบประมาณ` ตัวเดียวที่เป็น custom field จริงๆ** (ตัวเลข ไม่เข้าพวกป้าย)
