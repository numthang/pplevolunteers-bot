## 🎯 ที่มา

งานขององค์กรกระจัดกระจาย — ตอนนี้ "งาน" อยู่ 5 ที่ ไม่มีที่ไหนเห็นภาพรวม:

| อยู่ที่ไหน | เป็นงานแบบไหน | ปัญหา |
|---|---|---|
| **Discord chat** | สั่งงานปากเปล่าในห้อง | ไหลหาย ไม่มีสถานะ ไม่มีคนรับผิดชอบ |
| **Cases** | เรื่องร้องเรียนจากประชาชน | มี lifecycle ครบ แต่ครอบเฉพาะเรื่องร้องเรียน |
| **Posts** | งานคอนเทนต์ | มีสถานะร่าง/อนุมัติ/เผยแพร่ แต่ไม่มี "ใครทำ ภายในเมื่อไหร่" |
| **Calling** | งานโทร | มี assignment แต่ผูกกับรายชื่อ ไม่ใช่งานทั่วไป |
| **หัวคน** | ที่เหลือทั้งหมด | 😐 |

**สิ่งที่ยังไม่มี:** งานที่ไม่เข้าพวกไหนเลย — จัดอีเวนต์ · เตรียมเอกสารยื่นหน่วยงาน · ตามงบ · ประชุม · onboard อาสาใหม่ · ทำป้าย · ประสานพื้นที่

## ⛔ กับดักที่ทั้งดีไซน์นี้พยายามเลี่ยง — "ที่เก็บงานที่ 6"

ถ้าทำบอร์ดการ์ดที่**ไม่รู้จักระบบอื่นเลย** มันจะไม่ได้ไปรวมงาน 5 ที่ข้างบน แต่จะกลายเป็น**ที่ที่ 6** → กระจัดกระจายกว่าเดิม

**กลไกการตายที่จะเกิดจริง:**

```
วันจันทร์  ประชาชนแจ้งถนนพัง → ระบบเคส สร้าง 70-69-A8F3  [กำลังดำเนินการ]
วันจันทร์  ทีมอยากตามงานนี้  → สร้างการ์ด "ตามเคสถนนพัง"  [กำลังทำ]
           ↑ เรื่องเดียวกัน อยู่ 2 ที่แล้ว

วันศุกร์   เจ้าหน้าที่ปิดเคสในระบบเคส → 70-69-A8F3  [แก้ไขแล้ว] ✅
           ไม่มีใครไปลากการ์ดในบอร์ด → การ์ดยังค้าง  [กำลังทำ] ❌
```

**บอร์ดโกหก** → คนจับได้ 2-3 ครั้ง → เลิกเชื่อ → เลิกอัปเดต → เลิกใช้
นี่คือเหตุผลที่ทีมส่วนใหญ่ทิ้ง Trello ใน 2 เดือน ไม่ใช่เพราะ Trello ไม่ดี แต่เพราะ**ไม่มีใครอยากอัปเดตข้อมูลเดียวกัน 2 รอบ**

**ทางแก้ที่ยึดทั้งดีไซน์:** การ์ดที่ผูกของจริง **ไม่เก็บสถานะเอง** — ชี้ไปที่เคส/โพสต์ แล้ว**คำนวณสถานะสดทุกครั้งที่แสดง** เคสปิดเมื่อไหร่ การ์ดขึ้น "เสร็จ" เองทันที ไม่ต้องมีใครลาก

> จุดแข็งที่ Trello/Notion ให้ไม่ได้ และเราให้ได้ คือ *งาน ↔ เคสจริง ↔ โพสต์จริง ↔ คนจริง ↔ Discord* อยู่ในฐานข้อมูลเดียวกัน
> **ถ้าดีไซน์แล้วสุดท้ายได้ Trello ที่ช้ากว่า Trello — แปลว่าดีไซน์ผิด**

## 🧩 หัวใจของดีไซน์ — ช่องมี "ประเภท" ซ่อนอยู่ข้างหลัง

ทีมตั้งช่องได้อิสระ (กี่ช่องก็ได้ ชื่ออะไรก็ได้) แต่**ทุกช่องต้องติดประเภทที่ระบบรู้จัก**

```
กระดานทีมสื่อ  (ทีมตั้งชื่อเอง)
┌─────────┬──────────┬────────────┬───────────┬──────────┐
│ ไอเดีย  │  เขียน   │ บ.ก. ตรวจ  │ รอคิวลง   │  ลงแล้ว  │  ← ชื่อที่ทีมตั้ง
├─────────┼──────────┼────────────┼───────────┼──────────┤
│ รอทำ    │ กำลังทำ  │  รอตรวจ    │ พร้อมส่ง  │  เสร็จ   │  ← ประเภท (ระบบรู้จัก)
└─────────┴──────────┴────────────┴───────────┴──────────┘

กระดานทีมธุรการ  (คนละหน้าตา ใช้แค่ 3 ช่อง)
┌─────────┬──────────┬──────────┐
│ ยังไม่ทำ│  ทำอยู่  │  จบแล้ว  │
├─────────┼──────────┼──────────┤
│ รอทำ    │ กำลังทำ  │  เสร็จ   │
└─────────┴──────────┴──────────┘
```

**บรรทัดล่างคือสิ่งที่ทำให้ 3 อย่างนี้เป็นไปได้:**
1. โพสต์ `review` โผล่มา → หาช่องประเภท "รอตรวจ" → วางถูกเอง
2. หน้า "การบ้านของฉัน" รวมทุกกระดานได้ เพราะบรรทัดล่างพูดภาษาเดียวกัน
3. ย้ายการ์ดข้ามกระดานได้ — หาช่องปลายทางที่ประเภทตรงกัน

> ไม่ใช่ของที่คิดเอง — Jira เรียก *status category* · Linear เรียก *status type* · GitHub Projects ใช้แนวเดียวกัน
> ทุกเจ้าที่โตเกิน Trello ลงเอยที่ทางนี้หมด เพราะเจอกำแพงเดียวกัน

## 🎨 ประเภทสถานะ — 6 แบบ (ห้ามเพิ่ม/ลด ทั้งระบบ)

| # | ประเภท | key | โพสต์ (`post_episodes`) | เคส (`cases`) |
|---|---|---|---|---|
| 1 | **รอทำ** — ยังไม่มีเจ้าภาพ | `backlog` | — *(โพสต์มีเจ้าของเสมอ)* | `open` |
| 2 | **กำลังทำ** | `doing` | `draft` | `in_progress` |
| 3 | **รอตรวจ** — รอ บ.ก./รออนุมัติ | `review` | `review` | — |
| 4 | **พร้อมส่ง** — ตรวจผ่าน รอถึงคิว | `ready` | `approved` | — |
| 5 | **เสร็จ** | `done` | เผยแพร่แล้ว *(คำนวณสด)* | `resolved` · `closed` |
| 6 | **พักไว้** — ยังจะทำ แต่หาคนทำไม่ได้/ไม่ใช่ตอนนี้ | `cancelled` | — | `rejected` |

**⚠️ ข้อ 6 เปลี่ยนป้าย 2 รอบ (key ใน DB ยังเป็น `cancelled` เสมอ):** "ยกเลิก" → "กรุ" (2026-08-17) → **"พักไว้" (2026-08-18)**
user ไม่เคยใช้ "ยกเลิก" เลย (0 ใบ — งานที่ไม่เอาเขาลบทิ้ง) แต่ต้องการที่พักงานที่ยังไม่ทำตอนนี้
· ผ่อน DB CHECK แล้ว: การ์ดที่**ยังไม่มีเจ้าภาพก็พักไว้ได้** (เดิมไม่มีเจ้าภาพอยู่ได้แค่ `backlog`)
· พักไว้ **ไม่ตั้ง `completed_at`** — ไม่ใช่งานที่ทำจบ · เอากลับ = ลากออกจากช่อง
· ⚠️ ก้อน 4: เคสที่ถูกปฏิเสธ (`rejected`) จะไหลมาลงช่องนี้ด้วย — ถ้าถึงตอนนั้นแล้วปนกันจนงง
  ค่อยแยกเป็นธงต่างหาก **ห้ามเพิ่มประเภทที่ 7**

### ⭐ "พักไว้" กับ "กรุ" คนละของ — ห้ามยุบเข้าหากัน (เคาะ 2026-08-18)

คำเคยแปะสลับกันจนงง: ช่องที่ชื่อ "กรุ" ไม่ใช่ archive ส่วนของที่เป็น archive จริงกลับเขียนว่า "ลบ"

| | เก็บที่ | เห็นที่ไหน | กลับมายังไง |
|---|---|---|---|
| **พักไว้** | `status_type = 'cancelled'` | กองหนึ่งบนหน้า `/kanban` ตามปกติ | ลากออกจากกอง |
| **กรุ** = archive | `archived_at` | โหมด **"แสดง: กรุ"** | ปุ่ม "เอาออกจากกรุ" |

- ปุ่มในการ์ดคือ **"เก็บเข้ากรุ"** (`DELETE` → `archiveCard`) · เอาออก = `PATCH { restore: true }` → `unarchiveCard`
- ด่านสิทธิ์ 2 ทางใช้ `canArchiveCard()` ตัวเดียวกัน (คนสร้าง หรือ admin)
- **โมดูลนี้ไม่มี hard delete เลย** — ไม่มี `DELETE FROM kanban_cards` ที่ไหนในโค้ดแอป
- ⚠️ commit `37dd5e6` เคยแยก "ลบ" ออกจาก "กรุ" เพราะตอนนั้นปุ่มเขียน "เก็บเข้ากรุ" แต่ทำงานเป็นลบถาวร = โกหก
  **รอบนี้เอาคำกลับมาได้เพราะมีโหมดดูกรุ + ปุ่มเอาออกแล้ว** — ไม่ใช่การถอย อย่าแก้กลับ
- ⬜ ยังไม่มี auto-purge — การ์ดในกรุอยู่ตลอดกาล (ยังไม่มีใครขอ)

**⛔ "ติดปัญหา" ไม่ใช่ประเภท — เป็นธงบนการ์ด** (`blocked` + `blocked_reason`)
เพราะงานที่ติดปัญหา*ยังเป็นงานที่กำลังทำอยู่* ถ้าทำเป็นช่องแยก คนจะลากไปกองแล้วลืม แถมเสียข้อมูลว่าเดิมค้างขั้นไหน

### ⭐ กฎเหล็ก — การ์ดที่ผูกของจริงไม่เก็บสถานะเอง

> **การ์ดที่มีแถวใน `kanban_card_links` → `column_id` ไม่ใช่ source of truth**
> ต้อง**คำนวณช่องสดจากสถานะ entity ทุกครั้งที่แสดง** ตามตาราง §ประเภทสถานะ

ถ้าเผลอเก็บสถานะซ้ำไว้บนการ์ด = กลับไปเป็น "ที่เก็บงานที่ 6" ทันที ทั้งดีไซน์นี้พังทั้งอัน

**การ์ดโพสต์เกิดยังไง (lazy upsert):** เมื่อโพสต์ `visibility='org'` เข้าเกณฑ์ `kanban_board_sources` ของบอร์ดไหน → upsert แถว `kanban_cards` + `kanban_card_links(is_auto=true)` ครั้งเดียว
ต้องมีแถวจริง (ไม่ใช่ virtual) เพราะ user เคาะให้การ์ดมี checklist / คอมเมนต์ / คนช่วย / ป้าย ซึ่งต้องมีที่เก็บ

### ⚠️ ประเด็นที่ต้องระวัง (บทเรียนจากโปรเจกต์นี้)

- **`entity_type` ต้องใส่ทุก query เสมอ** — เคสเดียวกับ `contact_type` ใน calling
  `cases.id` กับ `post_episodes.id` ช่วงเลขทับกันแน่นอน → ทุก JOIN/WHERE บน `kanban_card_links` ต้องมี `AND entity_type = '...'`
- **`due_at` เป็น local Thai time จากฟอร์ม** — ห้าม `new Date(x).toISOString()` ให้ pass ตรงๆ ให้ pg (เคสเดียวกับ `txn_at`)
- **`org_id` ต้องมีตั้งแต่ตารางแรก** — ไม่ต้องเจ็บซ้ำแบบ finance ที่ retrofit scope ทีหลัง
- **`ref` = `<board.key>-<เลขรัน>`** เช่น `MEDIA-42` (พูดถึงกันใน Discord ได้) — เลขรันต่อบอร์ด ไม่ใช่ต่อ org
- **หลัง migration ต้องเช็ค index ตามมาครบ** — `SELECT indexdef FROM pg_indexes WHERE tablename LIKE 'kanban%'`

## 🔐 สิทธิ์

**เห็นบอร์ด** = ผ่านเงื่อนไขใดข้อหนึ่ง:
1. `open_to_org = true` และเป็นสมาชิก org
2. มียศตรงกับแถวใน `kanban_board_permissions`
3. มีชื่อใน `kanban_board_members`
4. เป็น `admin` / `secretary_general` (เห็นทุกบอร์ด — เหมือน scope calling/case)

**ไม่สร้าง permission ใหม่ระดับ org** — ใช้ยศเดิมที่มีใน `lib/permissions.js`

**ลากการ์ดที่ผูกของจริง** — ต้องผ่านด่านของระบบต้นทาง ไม่ใช่ด่านของ kanban:

| ลากจาก → ไป | เท่ากับ | ด่านที่ต้องผ่าน |
|---|---|---|
| รอตรวจ → พร้อมส่ง | อนุมัติโพสต์ | `canApprove()` — `web/lib/postsAccess.js:41` |
| พร้อมส่ง → กำลังทำ | ถอนอนุมัติ/ขอแก้ | `canRequestChanges()` — บรรทัด 112 |
| กำลังทำ → รอตรวจ | ส่งให้ตรวจ | `canEditPost()` — บรรทัด 100 |
| ? → เสร็จ | เผยแพร่ | **ลากไม่ได้** — ต้องผ่านกล่องเผยแพร่ (เลือกแพลตฟอร์ม/บัญชี/เวลา) |

ไม่ผ่านด่าน → **การ์ดเด้งกลับช่องเดิม + toast บอกเหตุผล** (ห้ามเงียบ)

### ⛔ ด่านที่ 2 — optimistic lock ของโพสต์ (เจอตอน `/scrutinize`)

[`setPostStatus`](../../web/db/posts/episodes.js#L274) เขียน `updated_at = now()` **โดยไม่เช็ค lock** และ `updated_at` คือ lock token ของ autosave ([บรรทัด 15](../../web/db/posts/episodes.js#L15))

```
พี่เอกำลังพิมพ์โพสต์อยู่ /posts       (ถือ lockToken = T1)
บรรณาธิการลากการ์ดใบนั้นบนบอร์ด      → setPostStatus → updated_at = T2
พี่เอพิมพ์ต่อ → autosave ส่ง T1        → 409 บล็อกการเซฟ (ไม่ใช่ last-write-wins)
```

→ **ก่อนลากการ์ดที่ผูกโพสต์ ต้องเช็คว่ามีคนเปิดแก้อยู่ไหม** ถ้ามี ให้เตือนก่อน หรือกันไม่ให้ลาก
→ ห้ามเรียก `setPostStatus` ตรงๆ จาก kanban โดยไม่ผ่านชั้นที่รู้เรื่อง lock

**กฎที่ห้ามต่อรอง:**
- ⛔ **โพสต์ `visibility='personal'` ห้ามโผล่บนบอร์ดใดๆ ทั้งสิ้น** — POSTS.md ระบุว่าเป็นที่เก็บเรื่องอย่างจุดยืนการเมือง/ค่าตอบแทนที่ยังไม่พร้อมให้ทีมเห็น
- ⚠️ **Debug mode `discordId = null`** → ownership check พังเงียบ ต้องเทสโหมด "View as role" ก่อน ship

**ไม่ต้องมีโหมด personal ระดับการ์ด** — อยากได้การบ้านส่วนตัว = สร้างบอร์ดที่ไม่เชิญใครและไม่เปิด org (ประหยัด 1 คอลัมน์ + edge case ทั้งชุด)
