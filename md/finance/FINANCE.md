## 3. Slip OCR — อ่านบันทึกช่วยจำอัตโนมัติ

### Flow
```
user ส่ง slip รูปใน Discord thread
  → Tesseract.js อ่านรูป
  → parse ข้อมูลจาก slip:
      - ref_id (เลขที่รายการ)
      - จำนวนเงิน
      - เลขบัญชีผู้รับ
      - บันทึกช่วยจำ ← ใช้เป็น note/category hint
  → validate ref_id ตรงกับ transaction ที่รอ category
      ตรง → update note + category อัตโนมัติ
      ไม่ตรง → แจ้ง error "slip นี้ไม่ตรงกับรายการที่รอยืนยัน"
  → Bot mention เหรัญญิกถ้า category ยังไม่รู้จัก
```

### ตัวอย่าง slip K-Plus ที่ parse ได้
```
เลขที่รายการ: 016098205038BTF04425  → ref_id
จำนวน: 1.00 บาท                    → amount (ใช้ validate)
เข้าบัญชี: xxx-x-x7749-x           → match account
บันทึกช่วยจำ: ทดสอบหมวดหมู่        → note + category hint
```

### Validation Rules
- ส่ง slip ห้องไหนก็ได้ใน Discord
- match account จากเลขบัญชีใน slip ก่อน
- ถ้า slip เป็นบัญชีที่ไม่ได้ผูกกับระบบ → แจ้ง error
- ถ้า ref_id ซ้ำ (เคย process แล้ว) → แจ้งว่า "รายการนี้ถูกบันทึกแล้ว"

### Library
- Tesseract.js (ฟรี รันบน server)
- ถ้าแม่นไม่พอค่อย switch ไป Google Vision API

## SMS Webhook vs Email — ทำไม reject expense SMS

KBank แจ้งเตือนทั้งสองช่องทาง แต่ละช่องทางให้ข้อมูลต่างกัน:

| ทิศทาง | ช่องทาง | ข้อมูลที่ได้ |
|---|---|---|
| รายรับ (income) | SMS → smsWebhook | จำนวน, ยอดคงเหลือ, ชื่อผู้โอน |
| รายจ่าย (expense) | Email → emailPoller | ref_id, ชื่อผู้รับ, ธนาคาร, ค่าธรรมเนียม, ยอดคงเหลือ |

**ดังนั้น `kbankSms.js` parser reject SMS รายจ่ายโดยตั้งใจ** — ใช้ email แทนเพราะให้รายละเอียดมากกว่า

**ข้อควรระวัง:** บัญชีที่ไม่ทำ email forward (forward แค่ SMS) จะบันทึกได้เฉพาะรายรับเท่านั้น รายจ่ายจะหายไป

### Format เลขบัญชี KBank ที่ mask ต่างกัน

KBank account format: `XXX-X-XXXXX-X` (3-1-5-1 หลัก รวม 10 หลัก)

| ช่องทาง | ตัวอย่าง | ตัวเลขที่เห็น | วิธี match |
|---|---|---|---|
| SMS | `บช X-4882` | 4 ตัวท้ายของกลุ่ม 5 หลัก | `accNo.endsWith('4882')` |
| Email | `xxx-x-x6488-x` | 4 ตัวรองสุดท้าย (กลุ่ม 5 หลัก, ไม่รวม check digit) | `accNo.includes('6488')` |

SMS และ email ของบัญชีเดียวกันให้ตัวเลขคนละชุด → ใช้ logic match ต่างกัน

## กองเงิน (finance_funds) + กองตามช่วงวันที่

แยกเงินหลายก้อนในบัญชีเดียว (เช่น ทุนทั่วไป vs รับบริจาครอบ "สู้น้ำท่วมสงขลา") · เคาะ 2026-09-18

- **กองมีวันที่** (`starts_at` ไม่ว่าง) — เงิน**เข้า**ที่ `txn_at` อยู่ในช่วงและยังไม่มีใครเลือกกองให้ → นับเป็นของกองนั้นเอง · `ends_at` ว่าง = ยังเปิดรับ
- **คิดตอนอ่าน ไม่เขียน `fund_id`** → ทางเข้าเงินอัตโนมัติ 5 ทาง (smsWebhook/emailPoller/financeOCR/parse-kbank-statement/web API) ไม่ต้องรู้เรื่องกองเลย · แก้วันที่มีผลย้อนหลังทันที
- กฎอยู่ที่เดียว: `effectiveFundSql()` ใน `web/db/finance/funds.js` — ทุก query ที่แยกยอด/กรองตามกอง**ต้องใช้ตัวนี้ ห้ามใช้ `t.fund_id` ดิบ** (ไม่งั้นรายการที่เข้ากองอัตโนมัติหาย)
- `fund_manual` = มีคนกดเลือกกองเองแล้ว (รวม "ไม่ระบุ") → กองมีวันที่ไม่จับอีก · ไม่มีคอลัมน์นี้ กด "ไม่ระบุ" แล้วรายการจะเด้งกลับเข้ากอง · ลบกอง = ล้าง `fund_manual` ของรายการในกองด้วย
- รายจ่ายไม่ถูกจับอัตโนมัติ (รายจ่ายของรอบบริจาคมักเกิดหลังปิดรับ) · นอกช่วง = "ไม่ระบุกอง" (ตั้งใจไม่ทำ "กองหลัก" — ไม่ระบุกอง = ตัวเตือนว่ายังไม่มีใครจัด)
- ช่วงวันที่ของกองในบัญชีเดียวกันห้ามทับ — เช็คใน `web/lib/fundRange.js` (ไม่ใช้ EXCLUDE constraint เพราะต้องลง btree_gist)
- ยังไม่ทำ: `/finance/report` แยกตามกอง · โอนเงินระหว่างกอง

## รอบจ่ายเบี้ยเลี้ยง (finance_payout_rounds / _items)

จ่ายเงินให้คนหลายคนพร้อมกันหนึ่งรอบ — ออกไฟล์โอนกลุ่มเข้า K BIZ แล้วตามเก็บว่าใครได้เงินแล้ว/แจ้งแล้ว
หน้า: `/finance/payouts` (รายการรอบ) · `/finance/payouts/[id]` (รายชื่อในรอบ)

### เส้นทางการใช้งาน

สร้างรอบ → ใส่รายชื่อ → **ออกไฟล์โอน** → เอาไฟล์ไปอัปโหลด K BIZ → ติ๊ก "จ่ายแล้ว" รายคน → **แจ้ง DM** → ปิดรอบ

- รอบผูกกับ **บัญชีต้นทาง 1 บัญชี** · ที่มาเป็นกิจกรรม (`event_id`) หรือช่วงเดือน (`period_ym`) อย่างใดอย่างหนึ่ง
- ผู้รับเป็น **XOR**: `member_user_id` (สมาชิก) หรือ `external_payee_id` (คนนอก จาก `docs_external_payees`)
  — CHECK `finance_payout_items_recipient_xor` บังคับ ทุกที่ที่เขียนผู้รับต้องส่งสองคอลัมน์พร้อมกัน
- รายชื่อถูกแบ่งเป็น **กลุ่มละ 10 คน** (`chunkIntoGroups`) ตามเพดานรายการต่อครั้งของแอปธนาคาร
- **ลอกรายชื่อจากรอบก่อนได้** (`copyItemsFromRound`) — ยอดใช้ `default_amount` ของรอบปลายทางก่อน

### สถานะ: DB มี 3 ค่า · จอโชว์ 6 ขั้น

| ใน DB | เกิดตอน |
|---|---|
| `draft` | สร้างรอบ |
| `exported` | กดออกไฟล์โอน**ครั้งแรก** (`export/route.js` เลื่อนให้เฉพาะตอนยังเป็น draft) |
| `paid` | กดปุ่ม "ปิดรอบ" เอง — ต้องติ๊กจ่ายครบทุกคนก่อน |

ป้ายบนจอคำนวณจากตัวเลขจริงใน **`web/lib/payoutStage.js`** (เทส `payoutStage.test.js`):
ร่าง → เตรียมโอน → โอนแล้ว n/m → โอนครบ·รอแจ้ง → **แจ้งโอนแล้ว** → ปิดรอบแล้ว

- ⛔ **ห้ามเพิ่มค่าที่ 4 ลง CHECK constraint** — "แจ้งโอนแล้ว" เป็นผลรวมของการกดรายคนที่กดซ้ำได้
  และบางคนแจ้งไม่ได้ถาวร → เก็บเป็นค่าเดี่ยวใน DB เมื่อไหร่ก็เพี้ยนจากความจริงเมื่อนั้น
- ⛔ **รอบที่ไม่มีใครแจ้งได้เลย (คนนอกล้วน) ห้ามขึ้น "แจ้งโอนแล้ว"** — `notified >= notifiable` เป็นจริง
  แบบว่างเปล่าตั้งแต่ `0 >= 0` ทั้งที่ไม่เคยส่ง DM สักฉบับ → ตกไปขั้น "โอนครบแล้ว" แทน
- `status='paid'` = **ปิดรอบ** ไม่ใช่จังหวะเงินออก (เงินออกตอนติ๊ก `paid_at` รายคน) ป้ายจึงเขียนว่า "ปิดรอบแล้ว"

### snapshot ตอน export — ทำไมข้อมูลผู้รับถึงไม่วิ่งตามทะเบียน

`finance_payout_items` มีคอลัมน์ `payee_name/payment_method/bank_code/account_no/promptpay_id/snapshot_at`
ว่างไว้ตอนแรก → `ITEM_SELECT` อ่านสดจากทะเบียน (`org_members` / `docs_external_payees`) ด้วย COALESCE
**พอกด export จะ `snapshotItems()` เขียนค่าตอนนั้นลงแถว** แล้ว COALESCE จะหยิบ snapshot มาก่อนทะเบียน

→ ใครมาแก้เลขบัญชีตัวเองทีหลัง ประวัติรอบเก่าไม่เปลี่ยนตาม และตรงกับไฟล์ที่อัปโหลดเข้าธนาคารไปแล้ว
→ ⚠️ `org_members` มีได้**หลายแถวต่อ user** (แถวละ guild) — ITEM_SELECT ใช้ `LEFT JOIN LATERAL … LIMIT 1`
   เลือกแถวที่มีเลขบัญชีก่อน · JOIN ตรงๆ = รายการในรอบซ้ำ 3 เท่า

### ออกไฟล์โอน

- `validateItems()` ตรวจก่อนเสมอ — ข้อมูลไม่ครบตอบ 422 พร้อม**รายชื่อคนที่ขาด** ขึ้นธงแดงรายบรรทัด
  (ไฟล์ที่ข้อมูลไม่ครบโดน K BIZ ตีกลับทั้งไฟล์ ซึ่งรู้ตอนนั้นสายไปแล้ว)
- รูปแบบไฟล์อยู่ `web/lib/payoutExport/` (`generic-csv` เป็นค่าเริ่มต้น) · `plainText.js` ใช้กับปุ่มคัดลอก
- ⛔ **แก้บัญชีต้นทางของรอบย้อนหลังไม่ได้** — `account_id` ถูกถอดออกจาก whitelist ของ `updateRound()`
  โดยตั้งใจ (2026-09-19) เพราะ exporter เขียนบัญชีต้นทางลงไฟล์ไปแล้ว และโมดูลนี้ไม่มี audit log

### แจ้งโอนทาง Discord DM

- `canNotify(item)` = `unreachableReason()` + ติ๊กจ่ายแล้ว · เหตุผลที่แจ้งไม่ได้: `external` (คนนอก ไม่มีบัญชีผู้ใช้) ·
  `no_discord` (สมาชิกยังไม่ผูก Discord) · `no_account` (ไม่มีทั้งเลขบัญชีและพร้อมเพย์) · `not_paid`
- ข้อความประกอบใน `web/lib/payoutNotify.js` (pure · เทส `payoutNotify.test.js`) — เลขบัญชี **mask เหลือ 4 ตัวท้ายเสมอ**
  เพราะ DM ไปอยู่บนเซิร์ฟเวอร์ Discord ถาวร · ภาษา**ล็อก th** ด้วย `createTranslator` ไม่ใช้ locale ของคนกดปุ่ม
- ⛔ **ส่งไม่ผ่าน = ไม่เขียน `notified_at`** (Discord 50007 = ผู้ใช้ปิด DM) ไม่งั้นได้ log ที่โกหกว่าแจ้งแล้ว
- ⛔ `notified_at` / `notify_count` เป็น**ร่องรอยเฉยๆ ห้ามเอาไปบล็อกการส่งซ้ำ** — กดซ้ำได้ไม่จำกัดโดยตั้งใจ
- **ปุ่ม "แจ้งทุกคนที่จ่ายแล้ว" = เบราว์เซอร์วนเรียก route รายคนทีละคน เว้น 300ms** ไม่ใช่ route ก้อนเดียว
  (50 คน ~20-40 วิ เสี่ยง nginx ตัดสายกลางทางทั้งที่ DM ออกไปแล้วครึ่งนึง แล้ว client ไม่รู้ว่าใครได้แล้ว)
  · ติ๊กจ่าย = ส่ง · **ไม่ข้ามคนที่แจ้งแล้ว** (ป๊อปยืนยันบอกจำนวนคนที่จะได้ซ้ำก่อนยิง)
- ⛔ **ห้ามผูกการส่ง DM เข้ากับ checkbox ติ๊กจ่าย** — ติ๊กพลาดติ๊กออกได้ DM ที่ออกไปแล้วเอาคืนไม่ได้

### สิทธิ์

- **สิทธิ์รอบ = สิทธิ์ของบัญชีต้นทาง** (`canViewAccount` / `canEditAccount`) ไม่มี ACL ชุดที่สอง —
  คนจ่ายแยกตามเขต/จังหวัดอยู่แล้ว · ทางเข้าเดียวคือ `web/app/api/finance/payouts/_guard.js`
- รอบที่ `status='paid'` → ทุก write ตอบ **409** · flag `allowPaid` ข้ามข้อนี้ได้
  ⛔ **ใช้ที่เดียวเท่านั้นคือ route แจ้ง DM** (รอบที่ปิดแล้วคือจังหวะที่ต้องแจ้งพอดี) ห้ามเอาไปใส่ route ที่แก้ยอด/รายชื่อ/สถานะ

### จุดที่เคยพลาด (อย่าทำซ้ำ)

- **เลือกกิจกรรมผิดแบบเงียบๆ** — dropdown เดิมโหลด 100 ตัวล่าสุดมา filter ฝั่ง client บน 157 ตัว
  → ค้นไม่เจอแล้วคลิกโดนแถวแรก ได้กิจกรรมคนละจังหวัด · แก้เป็น `EventCombobox` ค้นที่ server
  ต้องพิมพ์ ≥2 ตัว และ**ทุกแถวโชว์จังหวัด + วันที่**
- ⛔ **ห้ามเขียนกติกา "ใครแจ้ง DM ได้" เป็น SQL** — ข้อมูลผู้รับมาจาก COALESCE 3 ชั้น + LATERAL
  ลอกไปอีกที่ = กติกาแตกสองชุด → ใช้ `listItemsForRounds()` ดึงแถวจริงมาตัดสินด้วย `unreachableReason()` ฝั่ง JS
